# Security boundary

Status: experimental, self-tested, **not independently audited**. No promise of “undumpable”, malware-proof, or guaranteed fund safety is made.

## Threats addressed

An offline copy of the vault is protected by a password-derived key. Argon2id uses libsodium's moderate parameters: three operations and 256 MiB. Each new vault has a fresh 16-byte salt and 24-byte nonce. XChaCha20-Poly1305 authenticates the header and encrypted payload. The file is 160 bytes; no private address key is stored in plaintext. Decryption fails on a wrong password or authenticated-byte tampering. A weak password remains vulnerable to guessing.

The encrypted payload has three independent random 32-byte roots for BTC, LTC and SOL. EVM network keys are derived using libsodium's keyed derivation with the `AURUMEVM` context and distinct subkey IDs. The same network's stablecoins use that network's key. The code uses the OS-backed libsodium RNG, libsecp256k1 signatures, and libsodium Ed25519; it does not implement new signing primitives.

On Linux, startup sets `PR_SET_DUMPABLE=0`, the soft and hard `RLIMIT_CORE` limits to zero, and `PR_SET_NO_NEW_PRIVS=1`. Failure terminates startup. The verified test compares a readable unprotected child with a protected child: the latter rejects `process_vm_readv`, opening `/proc/<pid>/mem`, and `PTRACE_ATTACH` from the ordinary parent process.

Secret buffers use libsodium guarded allocations, checked `sodium_mlock`, explicit checked `MADV_DONTDUMP`, zero initialization, and automatic cleanup. Allocation/protection failure stops the operation. Key buffers become read-only after construction/decryption. Temporary Ed25519 secret keys and password-derived keys use the same guarded allocator. Password byte buffers are wiped on success and error. Wallet storage is written atomically with owner-only permissions. The live data directory is owner-only and one instance holds a filesystem lock.

Production creation, restore verification, address derivation and signing run in a separate, short-lived `aurum-signer` process. The GUI sends encrypted vault bytes and a password through an anonymous local socket pair; it never decrypts a private key. The password is sent directly from a locked allocation, outside Qt's queued I/O buffers, and that allocation is wiped after handoff. Command-line arguments, environment variables, JSON and temporary files never contain the password. The helper is started at a fixed sibling path with an explicit environment; it closes inherited descriptors and exits after exactly one operation. There is no persistent signing daemon.

Before reading password bytes, the helper installs a Linux seccomp syscall allowlist. It can read/write its inherited channel, allocate/protect/free memory, access randomness and clocks, use local anonymous pipes/signal stacks for diagnostic runtime checks, and terminate. Filesystem opens, sockets, process creation/execution, ptrace, cross-process memory operations and re-enabling dumpability are denied. Installation failure stops signing. A 30-second lifetime limit also applies. The helper links Qt Core and cryptographic libraries, without Qt Widgets, Qt Network or WebSockets. This is process separation with a syscall sandbox, not a VM or a defense against privileged code already executing on the host.

The signer checks that the decrypted public key matches the reviewed wallet. It only accepts supported transfer formats: network-matched BTC/LTC transfers, EVM native transfers or the selected stablecoin's ERC-20 transfer, and reconstructed native SOL/SPL messages. Arbitrary contract calls, token approvals and unexpected Solana instructions are rejected. The parent receives public addresses, encrypted vault bytes or a signed transaction; never a private key. Keys are wiped before a successful response, and process exit discards residual library stack/register state. Browsing retains public information only. The public account view remains open until it is manually locked or the app closes. Password verification still occurs on opening and on every send; decrypted keys are not retained. No password or private key is sent to a remote service or clipboard. Receive-address copying uses the clipboard intentionally.

Monero is handled by the signed upstream `monero-wallet-rpc` and optional `monerod` components rather than by Aurum's secp256k1/Ed25519 vault. The default endpoint is a public restricted onion node reached through the local Tor SOCKS proxy `127.0.0.1:9050`; Aurum does not silently fall back to a direct clearnet connection if Tor is unavailable. For the optional loopback endpoint Aurum starts `monerod` with RPC and peer listeners on loopback, inbound port advertisement disabled, and optional local SOCKS proxy routing. The wallet RPC child binds to `127.0.0.1` on a random local port, uses a per-launch random RPC login, disables core dumps, sets `PR_SET_DUMPABLE=0` and `PR_SET_NO_NEW_PRIVS`, and is terminated when Aurum locks or its parent exits. The on-disk XMR wallet and `.keys` file remain in Monero's encrypted format with owner-only permissions. Aurum verifies the startup/send password by closing and reopening the XMR wallet before calling `transfer`; it does not retain an XMR spend key or implement an alternate ring-signature path. A remote node can observe wallet queries and broadcasts, and protocol-level Monero privacy cannot make that node trustworthy; Tor changes the source IP visible to it but does not protect against a compromised host, Tor endpoint, or network observer.

The optional Mullvad control delegates account handling, WireGuard keys, routing and the kill switch to the official Mullvad client. Aurum passes the entered 16-digit account number to `mullvad account login`, clears the field immediately, and never writes it to settings or logs. Connecting Mullvad before Tor gives the intended VPN → Tor → node path; Aurum does not implement a replacement VPN protocol or claim to verify the host's routing table.

TLS verification is enabled. Cross-origin redirects are refused. Requests have response-size and time limits. A rate-limited response triggers host cooldown. Wrong-mainnet checks, exact integer amounts, address checksums, input ownership checks, fee caps, a separate review step, and non-repeated uncertain broadcasts reduce transaction errors. These are safeguards, not proofs that a remote node is honest.

## Threats outside this boundary

- Root, `CAP_SYS_PTRACE`, a compromised kernel, physical RAM capture, DMA, hibernation images and hypervisor access can bypass ordinary process protections.
- Private keys necessarily exist briefly in the signer’s RAM during derivation/signing. A separate process and brief lifetime reduce exposure; they do not make the bytes cryptographically invisible to a privileged memory dump. Library internals can have transient copies on stacks/registers that this code cannot certify as erased. Password entry uses Qt; GUI/input method buffers and OS input events are not all controlled by the secret allocator.
- Same-user malware may log keystrokes, alter clipboard contents, display fake windows, replace the executable/launcher or read the encrypted backup and try passwords offline. Dump protections do not prevent those attacks.
- Injected code or hostile libraries can intercept secrets. The launcher clears common injection environment variables but cannot establish that the executable, OS, plugins, or dependency files are trusted.
- Public services learn address queries and IP addresses, and may lie or fail. Genesis checks do not authenticate their reported chain state.
- No external audit, formal verification, fuzzing campaign, hardware-wallet integration, or mainnet acceptance run was performed. Automated checks cannot establish absence of theft or loss bugs.

Do not rely on this version to protect substantial funds. An independent review and a hardware signer are the next steps for a wallet meant to withstand an infected PC. Do not share a password, encrypted wallet file, secret key, or recovery material in a bug report.

Implementation references: [Linux seccomp filters](https://kernel.org/doc/html/latest/userspace-api/seccomp_filter.html), [PR_SET_DUMPABLE](https://man7.org/linux/man-pages/man2/pr_set_dumpable.2const.html), and the [GCC sanitizer runtime's local-pipe memory checks](https://github.com/gcc-mirror/gcc/blob/master/libsanitizer/sanitizer_common/sanitizer_posix_libcdep.cpp). Tests measure the controls described here on the listed Linux build.
